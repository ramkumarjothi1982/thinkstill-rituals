### 4. SwiftShader determinism measured; golden tolerance set

Measured by the capture and written to `qa/golden/v2/determinism.json`. The reference is a *cold* render: legacy flags, a fresh page per frame, ascending order.

| Run | Result |
|---|---|
| cold-repeat: a **second browser process**, fresh page per frame, **descending** order | **16/16 bit-identical** (max \|Δ\| 0) |
| warm-shuffled: one page, all 16 in a seeded shuffled order | 13/16 identical. 4.5 s, 6.5 s and 12.8 s differ by max 7, 5 and 10/255 over 692, 445 and 84 px (face plus its reflection). |
| sequential: one page, frames 0–18 in order like `render.mjs`, then frame 6 again | 5/5 bit-identical |
| history-cause: frame 18, then `Face.tmp` cleared, then frame 135 | 1/1 bit-identical (when warm without the clear: 692 px differ) |

Verdict:

- **SwiftShader is run-to-run deterministic**, so the golden pixel tolerance is set to **exact (0)**. The state tolerance is 1e-9, applied as `|a−b| ≤ 1e-9·max(1,|a|,|b|)`; the measured maximum is 0.
- Separately, v2 has a **render-history dependence**. Diagnosed with `/home/user/hm-work/tmp/history-exp*.mjs`: the face's scratch canvas `Face.tmp` keeps the same 1024×512 size, but `tube()` clears only the `bw×bh` corner it uses. A blurred `drawImage` at a fractional offset then reads stale texels just past that corner, left over from earlier and larger strokes. Drawing only the previous face reproduces the warm result to within 17 px at 1/255; clearing `Face.tmp` restores the cold result exactly.
- This is why the goldens are defined as cold renders and why the sequential reference exists (below).

## Sequential reference (beyond the plan)

The plan assumed that frames are pure functions of t. The warm-shuffled run showed they can depend on render history, so I added one more measurement: is a cold golden the same as the frame the approved master actually contains?

```

[sequential     3 s] frame 0 (0 s): sequential == cold golden
… (all 15 frame-aligned goldens) …
[sequential  1180 s] frame 447 (14.9 s): sequential == cold golden
[sequential  1188 s] H.264 stream BIT-IDENTICAL to the approved master
```

- Frames 0–449 were rendered in one page, in order, exactly as `render/render.mjs` does. Each frame's top-down RGBA sha256 is in `qa/golden/v2/sequential-frames.json`: 450 hashes, a full-length pixel golden that costs no disk.
- **All 15 frame-aligned cold goldens equal the in-sequence frames (15/15, max |Δ| 0).** That includes 4.5 s and 6.5 s, which differ only when frames are rendered *out of order*.
- The in-order frames were piped through render.mjs's exact encoder arguments (libx264 slow, CRF 16, film tune, `-g 30`, BT.709, vflip). **The resulting H.264 elementary stream is byte-identical to the approved `output/v2/my-brain-at-2am-v2.mp4`'s stream**: sha256 `bd761d96…6365` for both. This proves that today's frozen code, Chromium and x264 reproduce the approved master bit for bit.
- `tests/golden/v2-frames.test.mjs` keeps checking that `sequential-frames.json`, the cold goldens and the bitstream result agree.

## Deviations from the plan

1. **R2 flags.** The plan (WP-01, Risks) says to add `--use-angle=swiftshader --enable-unsafe-swiftshader`. Measured: those flags give **0/16 bit-identical frames, max |Δ| 49/255**, and render about 4× slower (about 15 s per frame against 4 s). The WebGL renderer string doesn't change, so the 2D canvas path probably changes. `--enable-unsafe-swiftshader` alone, and `--use-angle=vulkan --enable-unsafe-swiftshader`, are **3/3 bit-identical at the same speed**. Recorded as `RECOMMENDED_ARGS` in `tools/golden/v2-harness.mjs` and in `RISK-FIX-TABLE.md`. **WP-01 must use the vulkan variant.**
2. **Tag commit.** `v2-approved` is on `dfed2b6`, the commit that added `output/v2/*`, as instructed. `451caf0` later added only `my-brain-at-2am-v2.preview.mp4` (the same frames and audio) and a README change. The frozen code is identical in both. The hash-lock covers the preview because it is in HEAD.
3. **`audio/soundtrack.mjs` is frozen.** That follows the WP-00 hard rules. The plan's WP-04 file list says "audio/soundtrack.mjs (adds transposition and circular render)". **WP-04 must fork it** (for example into `audio/score.mjs` plus a shared engine module). This is noted in `CONVENTIONS.md`.
4. **Q3 default.** Recorded as "galleries local; previews ≤ 15 MB shareable" per the WP-00 brief. The synthesis's version, also publishing the gallery as a private claude.ai page, is recorded as an opt-in.
5. **Golden frame at 0.98 s.** It is not on a frame boundary (frame 29.4). It is rendered at exactly t = 0.98 via `renderFrame(29.4)`; `29.4/30 === 0.98` was checked. It has no PSNR against the MP4, and its 5 states are extra rows (`extra: true`).
6. **Golden frames are defined as cold renders,** because of the history dependence (criterion 4). The plan assumed frames are pure functions of t. They are, except for residue in v2's face scratch canvas when frames are rendered out of order. The sequential reference shows that cold renders equal the approved master's frames.
7. **`qa/golden/v2/frames/*.png`.** The PNGs live in `WORK`, with their hashes committed, as the brief requires. `.gitignore` also blocks the plan path.
8. **"No writes outside the studio root"** is enforced in three ways. A static `git status` check of the repository outside the studio. The app tree hash, which covers ignored files. `assertWritable()` for every tool's output paths. There is no runtime interception of `fs`, which would be intrusive and easy to bypass anyway.
9. **`render/serve.mjs`** is not hash-locked, because WP-01 lists it as its own file. The legacy route depends on it, so `legacy-route.test.mjs` pins its API (`startServer`, `REPO_ROOT`) and checks that it serves `stage2/index.html`.
10. **`npm test`** runs guard, unit and parity together (about 20 s, Chromium included), so that G-STATE/G-CUES/G-PLAN run on every hand-in. `test:golden` (pixels, about 2 min) is separate, as in the plan.

## Open issues and notes for later packages

- **WP-01 and WP-26 (segments and resume):**
  - A frame rendered in a fresh page equals the cold golden. On v2 that is also the in-sequence frame, at every golden time checked.
  - Out-of-order rendering inside one page is the only case measured to differ: up to 10/255.
  - So a segment should start in a fresh page and render in order. Resume then restarts the segment in a fresh page.
  - Not yet measured: whether *every* segment start, frames 90, 180, 270 and 360, also equals its in-sequence frame. WP-01 must check its segmented legacy render against all 450 hashes in `qa/golden/v2/sequential-frames.json`, which gives exact parity with the approved master, not just ≥ 60 dB.
  - If a segment start differs, the cheap fix is to replay the earlier `Face.draw` calls (Canvas2D only, no GL) before rendering it.
- **WP-02/WP-10** (face cache, 1/4-resolution glow): any change that clears or resizes the face's scratch canvas is a pixel change, gated by G-PIXEL.
- PSNR of the cold goldens against the approved MP4 (44.3–48.4 dB) measures only x264's CRF-16 loss plus grain. G-PIXEL compares against lossless goldens, never against the MP4.
- The heavy lock is advisory. Running `node render/render.mjs` directly bypasses it; use `npm run render`, or wrap the command with the lock.
- `tools/derive_noomi_hires.py` writes straight into the frozen `assets/noomi/`. Never run it as it stands. WP-07's `derive_mallow.py` must take an output directory and run under `npm run derive`.
- `node --test` glob arguments need Node ≥ 22; `package.json` now declares `"engines": {"node": ">=22.2"}`, since `zlib.crc32` is used too.
