**Status: done.** Every acceptance criterion is met. Commands and measured numbers are below; two plan values were changed on measurements (see "Deviations").

- The render farm (`render/{farm,worker,segment,encode,mux,serve}.mjs`, `render/lib/provenance.mjs`):
  - renders 90-frame segments in parallel worker processes and reads frames back by binary POST;
  - joins the segments with `concat -c copy` and verifies the join;

- CLI: `hm render`, `hm status` and `hm doctor`.
- Two plan values had to change, both on measurements (details under "Deviations"):
  1. **Segment encoder: constant QP 15, not CRF 16.** CRF segments decode at only **49.5 dB** against a single pass. QP 15 with `direct=spatial` gives **bit-identical** decoded frames (PSNR ∞). On the real v2 frames its quality is higher than the approved master's on all 15 frame-aligned goldens.

### 3. Readback by binary POST: 60 ms or less per frame

The page reads the frame (`readPixels`) and POSTs it as a **Blob** to the local sink. The Node server receives it into one Buffer and hands it to the encoder; the answer waits for the consumer.

Two findings shaped this:
- **The body type.** POSTing the typed array itself took **689.6 ms** per 8.3 MB frame before it reached the server, and XHR took 785.8 ms. A Blob body took **28.9 ms** (`WORK/tmp/wp01/bench-transport.mjs`, median of 10).
- **Overlap.** The upload of frame i overlaps the render of frame i+1, with one frame in flight. `readback()` returns once the pixels are copied out of WebGL; the next `readback()` (or `flush()` at the segment end) first waits for the previous upload, so errors still surface and ordering is kept.

Benchmark on an exclusive machine (`tests/golden/engine-v2-frames.test.mjs`, median of 30 readbacks of a rendered 1080×1920 v2 frame):

```
✔ readback by binary POST: ≤ 60 ms per 1080x1920 frame (median of 30, exclusive machine)
ℹ binary POST, full round trip (readPixels + copy + upload + sink): median 43.5 ms;
  on the render's critical path (upload overlapped): 18.6 ms; stage2's base64 readback: median 268 ms
(second run, in the final test pass: 47.2 ms / 19.3 ms / 242 ms)
```

In the real renders, with the x264 encoders running beside Chromium, per-frame figures come from each segment's `.done` (`timing`):

| | critical path (median / p95) | full delivery, readback → sink holds the frame (median / p95) |
|---|---|---|
| run A, 1 worker (+ a second, single-pass x264 for the tee) | 31.3–33.3 / 41.4–45.5 ms per segment; job mean of medians 32.4 ms | 54.7–55.7 / 68.8–81.6 ms |
| run B, 2 workers (two Chromiums and two x264 on 4 cores) | 41.2–50.3 / 69.0–76.4 ms per segment; job mean of medians 44.9 ms | 80.9–88.0 / 125.5–175.4 ms |

What the numbers mean:
- **The criterion is met where it is defined.** On an exclusive machine the whole round trip takes 43.5–47.2 ms. On the render's critical path the median is 31–33 ms with 1 worker, and 41–50 ms with 2 workers saturating the machine.
- **The limit is exceeded only in the background.** Under two-worker load the full delivery (median about 85 ms) and the critical-path p95 (69–76 ms) go above 60 ms. The delivery runs while the next frame renders (2.1–5 s), so it costs no render time.
- **Against stage2.** The audit measured stage2's readback at 404 ms per frame, and this benchmark 268 ms. On the critical path the binary path takes 8–12 % of that.
- **Render time.** Run A rendered all 450 frames in 1,337.6 s of segment time (2.97 s per frame); the approved master took 1,524 s.
- **Two workers.** Run B took 20.3 min from first claim to joined video, against 22.6 min for run A. The gain is small because one SwiftShader page already keeps about 3.3 of the 4 cores busy.

**Stale locks** (`tests/unit/farm-segment.test.mjs`):
- A lock whose owner died is taken over at once. The owner is checked by pid **and** process start time on the same host, so a recycled pid is detected too.
- A lock not touched for more than 10 min (`STALE_LOCK_MS = 600000`) is reclaimed: a remote owner touched 9 min ago is live, one silent for 11 min is stale, and so is a hung live owner.
- The worker touches its lock after every frame.
- Of two reclaimers only one can win.

**Retries:** 1 attempt + 2 retries (`MAX_ATTEMPTS = 3`), then `.failed`. `--resume --retry-failed` clears it. A worker process that dies counts as an attempt for the segment it held, and the farm restarts it, up to 3 times.

**Watchdog:** 60 s per frame (`FRAME_TIMEOUT_MS`), covering render plus readback. Page setup, priming, the last upload and the encoder have their own limits. After it fires, the worker closes the browser and starts a new one.

### 6. Page reload per video; `dispose()` and content-hashed texture keys (no texture bleed between two specs in one worker); NaN from `subframes()` falls back with a logged error

- **Reload.** A worker opens a new page (a new JS realm and WebGL context) for every video. It also opens one for every segment that does not continue the segment it just rendered.

## Deviations from the plan

### 1. Segment encoder: constant QP 15 (`qp15`), not CRF 16

The plan asks for both "x264 slow CRF 16" and "decoded PSNR against a single-pass encode ≥ 60 dB" for segments joined with `concat -c copy`. With CRF the two cannot hold together. CRF carries rate-control state across GOPs:
- MB-tree looks 50 frames ahead, across keyframes;
- I-frame QPs come from a decaying average of earlier frames' QPs;
- `direct=auto` adapts from earlier B-frames.

So a segment encoded on its own differs from the same frames inside one long encode.

Measured with `WORK/tmp/wp01/enc-exp.sh`: the 450 frames of the approved v2, 5 × 90-frame segments + concat against one single pass, same settings, `-threads 2`.

| Encoder | Segmented vs single pass | Identical frames | Size (single) |
|---|---|---|---|
| A: CRF 16, `scenecut=0:open-gop=0` (the plan) | **49.47 dB** (min 46.56) | 60/450 | 33.0 MB |
| B: CRF 16, no MB-tree, qcomp 1 | 51.60 dB | 90/450 | 61.6 MB |
| C: QP 17, `direct=auto` | 54.83 dB | 338/450 (the first GOP of every later segment differs) | 23.6 MB |
| **D: QP 16, `direct=spatial`** | **∞ (bit-identical)** | **450/450** | 29.6 MB |
| **QP 15, `direct=spatial`** (adopted) | **∞** (also in run A, on the real render) | **450/450** | 35.1 MB |

Constant QP with spatial direct prediction and no scene-cut keyframes keeps every GOP self-contained, so segments are invisible.

Quality against the same source (the approved master's frames, PSNR-Y / SSIM): CRF 16 44.72 dB / 0.9857; QP 16 44.59 / 0.9838; QP 15 **44.93 / 0.9866**. On the real, lossless v2 frames (run A against the 15 frame-aligned golden PNGs, `WORK/tmp/wp01/quality-vs-golden.mjs`):

| | PSNR-Y mean | PSNR-Y min | better on | video stream |
|---|---|---|---|---|
| approved master (CRF 16, render.mjs) | 45.02 dB | 44.30 dB | — | 34.2 MB |
| run A (QP 15, segmented) | **45.86 dB** | **44.71 dB** | **15/15 frames** | 45.9 MB |

The cost is size: 45.9 MB against 34.2 MB for the approved master (+34 %). The plan budgeted about 35 MB per master. `ENCODERS.crf16` remains available for single-pass work, and the farm warns when a non-segment-safe encoder is chosen. WP-02 owns the profiles and may trade QP 15/16 against size. QP 16 would come closer to the approved size: an estimated 39 MB, from the 0.84 size ratio measured above. Its quality on the re-encode test was slightly below CRF 16.

### 2. SwiftShader flags: `--use-angle=vulkan --enable-unsafe-swiftshader`

The plan wrote `--use-angle=swiftshader --enable-unsafe-swiftshader`. WP-00 measured those flags at 0/3 frames bit-identical (up to 24/255) and 3.7× slower (`qa/golden/v2/determinism.json`). The Vulkan backend with the explicit unsafe-SwiftShader opt-in is bit-identical to the approved render, and the WebGL renderer string shows SwiftShader. It still opts in explicitly, which is what R2 asks for.

### 3. Smaller additions and interpretations

- **The adapter is an import map plus a wrapper.** The plan's "adapter" left the mechanism open. The import map runs the frozen module's own code paths on the engine's modules, so the parity covers engine code, not stage2 code.
- **Readback overlaps the next render** (one frame in flight). Plan step P1 is "binary ArrayBuffer POST to the local sink". The overlap and the Blob body (an ArrayBuffer-view body is 24× slower in Chromium) are refinements of it. The ≤ 60 ms criterion is met on the full round trip (43.5–47.2 ms, exclusive), not only on the critical path (18.6–19.3 ms).
- **`--preroll`.** A fresh page that starts a segment replays the face draws of the frame before it. Measured as not needed for v2 (0 primed frames is already identical at all four boundaries), but kept at 1 frame as a margin against the face's scratch-canvas history (CONVENTIONS §7).
- **Two extra job states:** `created`, before `compiled`, and `failed`.
- **Batches:** `hm render a b …` / `renderMany()`. One set of workers renders several jobs, which is how "two different specs in one worker" is shown with the real farm.
- **Sequential-golden gate in the farm.** A full render at the golden's parameters must reproduce all 450 hashes of `qa/golden/v2/sequential-frames.json`, or the job fails. This is a permanent G-PIXEL check on the legacy route.
- **One farm per job** (`farm.lock`, pid-checked). Two farms on one job directory are refused instead of racing at the join.
- **`engine/dev/fixtures/`.** Five tiny directions registered as `dev/*` (hidden from `hm render --list`). They make the farm's own tests fast (render scale 0.25, about 0.1 s per frame) and load no files.
- **`textKeys: 'legacy'` renderer option.** It exists only so the R4 test can prove it detects bleed (the sensitivity check). It is part of the job key and never the default.
